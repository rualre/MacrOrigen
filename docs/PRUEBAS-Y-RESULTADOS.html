1. Resumen ejecutivo

La integración de intercambios quedó operativa y sin dependencia del modelo de lenguaje para calcular equivalencias. El motor recibe una asignación entera de intercambios por comida, multiplica los gramajes exactos de la base de datos y valida el plan completo contra las metas con tolerancia de ±3%.

Qué se validó

  • 8 grupos y 18 subgrupos de intercambio; poblaciones ADULTOS y NINOS en tipos, API y base de datos.
  • 44 de los 45 alimentos del catálogo tienen intercambio. El café sin azúcar se excluye porque no aporta energía ni macros relevantes.
  • Estados de trazabilidad: 30 VERIFICADO, 12 HOMOLOGADO, 2 DERIVADO, 0 PENDIENTE.
  • Optimización entera de intercambios, distribución por 3–6 comidas, gramos exactos y medida casera.
  • Regeneración de una comida con recálculo del día y reequilibrio determinístico.
  • Intercambio por el mismo subgrupo mediante /api/diet/swap, sin LLM, con validación ±3% y bloqueo por cupo/suscripción.
  • Prompt y tools de IA actualizados: la IA solo elige IDs; el motor multiplica gramajes y rechaza grupos incompletos.
  • Importador CSV/JSON con validación Zod, dry-run por defecto, exportación y aplicación opcional a PostgreSQL.
  • 10 cuentas con suscripción activa hasta 2099; contraseñas únicas generadas localmente y guardadas fuera de Git.
Límite de alcance: la tabla completa UdeA 5.ª edición 2023 no está disponible en acceso abierto. No se inventaron valores ni se presentaron como oficiales. La fuente inicial es GABA 2015 (ICBF/FAO), que adoptó la lista de intercambios UdeA/GIANH, con estados de verificación explícitos. El importador queda listo para cargar el archivo autorizado.

Entorno de ejecución

Fuentes y trazabilidad

  • GABA 2015 (ICBF/FAO): Tablas 26–45 para pesos/medidas caseras y Tabla 46 para perfiles promedio.
  • La lista nacional adoptó por consenso la lista de intercambios de la Universidad de Antioquia (GIANH).

  • La edición UdeA 2023 se declara como reservada y no se usa para inventar datos.
  • Estado por alimento: verificado, homologado, derivado o pendiente.

4.1 Criterios de aceptación

  • Nutrición: todas las metas diarias deben quedar dentro de ±3%; si un swap no puede mantenerlas, la API debe rechazarlo o el motor debe reequilibrar sin inventar gramajes.
  • Intercambios: mismo subgrupo, misma población, filtro de alérgenos y cantidad entera de intercambios.
  • Grounding: todo gramaje debe ser intercambios × gramosPorIntercambio; los nutrientes se recalculan desde el catálogo.
  • Acceso: 3 intentos gratuitos, bloqueo del cuarto, sesión firmada y suscripción activa para las 10 cuentas.

5. Contrato de la API de intercambio

Método / rutaEntradaSalida esperadaIA
GET /api/diet/swapalimentoId, intercambios, alergias, poblacion, origenAlimento origen, subgrupo, cantidad y equivalentes con gramos, medida casera, nutrientes y fuente.No
POST /api/diet/swapplan, comidaId, alimentoId, reemplazoIdPlan rehidratado, ingrediente reemplazado, nutrientes recalculados y validación ±3%.No
GET /api/alimentos/:id/equivalentesID de alimentoEquivalentes heredados del catálogo; 404 si no existen.No
POST /api/planes/intercambiarPlan, comida y alimentoCompatibilidad con el flujo anterior; recalcula el plan.No
Blindaje contra alucinaciones: el LLM solo recibe una asignación determinística de grupos por comida y devuelve IDs. El servidor valida que cada ID exista, que cubra los grupos requeridos y que no viole alérgenos. Luego el motor multiplica gramajes oficiales y recalcula todos los nutrientes. Si no hay proveedor o la respuesta es inválida, se usa el selector local determinístico.

6. Seguridad, acceso y operación

Controles verificados

  • Contraseñas con scrypt y salt único; comparación en tiempo constante.
  • Sesiones HttpOnly firmadas con HMAC y AUTH_SECRET de al menos 32 caracteres.
  • Cookies de invitado firmadas y cupo de 3 planes.
  • Rate limit en memoria; Upstash opcional para producción distribuida.
  • Validación Zod de perfil, plan y swap; IDs de alimento comprobados.
  • Nutrientes del cliente descartados y recalculados en servidor.
  • Cabeceras nosniff, DENY, referrer y permissions policy.
  • npm audit de producción: 0 vulnerabilidades.

Datos que no se versionan

  • .env.local y cualquier API key.
  • .data/auth.json y .data/cuentas-demo.csv.
  • Contraseñas de las 10 cuentas y tokens de sesión.
  • PDFs fuente descargados en .data/sources.

El archivo .vercelignore excluye .data, .env.local, .next y node_modules del despliegue.
